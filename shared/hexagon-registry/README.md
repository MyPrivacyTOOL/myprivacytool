# Hexagon registry (MPC-7466)

One list of the 54 web scan hexagons (41 always, 13 conditional): label, group, what it captures, value to the user,
truth level (measured / estimate / cannot be checked), confidence the code holds, and the FOUND / CHECKED AND CLEAR /
NOT CHECKED rule. `trust_score` is deliberately null: Chris has not defined it. Do not fill it in.

- Code copy: `registry.js` (plain ESM, imported by the website in `src/` and by `workers/scan-report`).
- **Reviewed record (source of truth for the content): https://app.notion.com/p/3f628547eaa7810fac20ce7fd5efdc36**
  If the two disagree, stop and ask; change both in the same task and say so in the Result Summary.
- Tests: `src/lib/hexagonRegistry.test.ts` (vitest, ids and labels match the detection code) and `registry.test.mjs` (node, runs where the Worker runs).
- Hexagon artwork: none exists. Each hexagon is an inline SVG with one emoji (`artwork.emoji`).
- 46 was a hard-coded display number, 52 is the grid capacity, 28 was never found in the code.
- `status.js` (MPC-7487): `captureStatus(id, value, ctx)` decides FOUND / CHECKED AND CLEAR / NOT CHECKED when the site captures a value; `src/lib/webScan.ts` saves it with the scan. It follows the `status` rules here; change a rule in the registry, this file and the Notion page together.
- `EMAIL_HEXAGONS`: the four email hexagons (MPC-7467), outside the 54 web hexagons. `workers/scan-report/scripts/sync-hexagons.mjs` builds the Worker's compact copy from this file.
- `score.js` (MPC-7471-F4): the one exposure score, bands and coverage, version `exposure-v1`. Reads category, severity (from `truth.sensitivity`) and the allowed statuses from this registry. Spec and open decisions: `docs/exposure-score-spec.md`. Tests: `score.test.mjs`. Change a weight, band or mapping there, in the spec and in the public explanation together.
- `counts.js` (MPC-7471-F2): `scanCounts(items, opts)` gives confirmed (X), checked (Y) and total (Z) for one scan; Z is derived from this registry (never typed). Definitions, wording and open decisions: `docs/scan-counts-mpc-7471-f2.md`.
- `catalogue.js` (MPC-8689): the complete footprint, 368 hexagons across 27 channels (the 366 of the approved discovery plus the 2 records-about-a-person items added by owner decision 2026-10-29; 101 defined = web 54 + email 7 + Telegram 30 + 10 X candidates built by CK-8502 under different ids (`code_ids`), plus 267 not built: 265 found in the platform documentation and the 2 records items, which have a check but stay `new`). The file name `hexagons-366.json` is kept. **Generated**, do not edit by hand: source is `hexagons-366.json` (the approved discovery, risk tiers approved 2026-10-28; risk high 92 / medium 208 / low 68, arrival A 201 / B 94 / C 64 / D 9), build with `node scripts/build-hexagon-catalogue.mjs`. `status: "new"` items never count in `scanCounts`, the exposure score (`exposure-v1`) or the 54 web total. `channels.js` `CHANNELS` lists all 27 channels (code = the id prefix, e.g. `tg.`, `ig.`). Test: `catalogue.test.mjs` (the 91 defined ids must equal the ids in the code; nothing renamed).
- `public/footprint/hexagons-366.json` is the `/footprint/` dataset (merged by id into the built-in web items by `curtain.json` `dataset`). `supabase/migrations/20261028180000_mpc_8689_hexagon_catalogue.sql` creates `public.hexagon_catalogue` (RLS on, anon and authenticated select only).
- `/hexagon/` (master risk page) and `/hexagon/<slug>/` (one page per hexagon) are built into `dist/` at deploy time by `scripts/generate-hexagon-pages.mjs` (postbuild); slugs come from the label, prefixed with the channel when two labels match. The "what it could be used for" text is general guidance generated from each hexagon's description and common misuse themes: review it before campaigns.
- `TELEGRAM_EXTRA_HEXAGONS` (MPC-8689 pilot, 6): built and checked by the Telegram baseline (`extraStates` in `workers/social-listeners/src/baseline-scan.ts`) but **outside** the 30, the Telegram risk number (out of 30), the web 54 and the exposure score until the owner approves a new score version. They stay `status: "new"` in the catalogue and are listed in `EXTRA_HEXAGON_IDS`; `footprint.js` counts them as checked. Fields verified against Bot API 10.3. Personal channel latest posts calls `getUserPersonalChatMessages` (limit 20) only when `getChat` returned a personal channel; a failed call is `not_checked`, and the posts are never stored or logged (only whether any came back). Not built from the owner-approved list: edits, reactions and poll answers, and blocked or unblocked us (each is a separate update type the baseline does not read; reactions also need `message_reaction` in `allowed_updates` and a chat the bot administers); bio in join request (`ChatJoinRequest.bio` is in the Bot API docs, but arrives only as a `chat_join_request` update in a chat the bot administers with `can_invite_users`); Mini App items (need a Mini App).
- Email extras (MPC-8689 pilot, 4): `workers/scan-report/lib/emailExtras.js` builds plus-tag alias, address type, tools the domain uses (TXT verification records) and mail transport protection (MTA-STS, TLS reporting). Same rules as the 7 email hexagons (found / clear / not_checked, domain-only DNS, address never sent), but **off unless `EMAIL_EXTRAS_ENABLED=true`**, stored as `signals` rows named `extra-<id>` (the live view only reads `email-*`), and never in the report email, the score or any count. Their ids are in `EMAIL_EXTRA_IDS`. Not built: the four "If they email us" checks (need an inbound Email Worker), subdomains and WKD (Tier 3 queued jobs), PGP key servers and web archive (held for an owner decision).
- Web extras (MPC-8689 pilot, 9): `src/lib/webExtras.ts`. Seven come from Cloudflare's request data through the new Worker route `GET /whoami-extra` (`workers/mpt-leads/worker.js`; `/whoami` is unchanged): postal area, IP timezone vs device clock, network distance, network owner, TLS handshake fingerprint, HTTP version, EU flag. Two run in the browser: exact device model (client hints; browsers that do not share it say "not checked") and clock offset. **Off unless `VITE_WEB_EXTRAS=true`**, shown in `RiskScore` under "Extra connection checks (not part of your score)", never in the exposure score, `scanCounts`, the 54 or a saved scan. Their ids are `WEB_EXTRA_IDS`. Not built: reverse DNS (would show the visitor's IP to a third-party resolver, which MPC-7350 rules out) and the four permission-prompt checks (GPS, camera and microphone names, notifications, contacts and clipboard), which need new prompts.
- Discord extras (MPC-8689 pilot, 11): `workers/social-listeners/src/discord-interactions.ts`, route `POST /webhook/discord`. A person runs our slash command and sees privately (ephemeral) what Discord sent with it: user id and account age, names, avatar, server tag, badges, language, context, server membership, purchases, command input, and (with `DISCORD_BOT_TOKEN`) banner and colour. Ed25519 signature checked on every request (401 otherwise), PING answered. **Off unless `DISCORD_SCAN=on`**, allow-listed Discord ids only (`DISCORD_PROBE_IDS`; empty = nobody), nothing stored, nothing logged from the payload, never in any score or count. Fields confirmed against docs.discord.com; whether `GET /users/{id}` needs a bot token is not stated there, so the banner check is "not checked" unless that call works. Not built: email and verified, linked accounts, server list, Nitro and 2FA (the person must sign in with Discord). **Needs a Discord application (public key, slash command registered) before it can run live.**
- Records about a person (MPC-8689, owner decisions 2026-10-29), channel `brokers` "Data brokers and news archives" (code `DB`), class B, access Verify, risk high, status `new`: `brokers.people_search_listing` ("Listing on a people-search site") and `brokers.news_archive_mention` ("Named in a news archive"). Code: `workers/social-listeners/src/records-check.ts`, ids in `RECORDS_EXTRA_IDS`. The only input is a page address the person supplies, with the name or email to look for: `/listing <https-url> <term>` and `/archive <https-url> <term>` in the Telegram bot. **Off unless `RECORDS_CHECK=on`**, allow-listed senders only (`PROBE_TELEGRAM_IDS`), outside the 54, `scanCounts` and the exposure score. Nothing is ever searched for. The Worker fetches that one address (at most 3 redirects, each to a public https address; no cookie, no referrer, no details about the person; 8 s and 1.5 MB limits) and looks for the typed text on the fetched page locally; the text goes nowhere else, nothing is stored, and logs hold counts only (kind, result, reason code). Results: `found` if the name or email is on the page; `clear` only if the page loaded normally and it is absent, or the site says the page no longer exists (404/410); a blocked, challenged, failed, timed-out, partial or non-page fetch is `not_checked`, never `clear`. Wipe step: for a found people-search listing the reply shows the service's stated removal route, labelled "stated by the service" (only for a host whose page has been read: Spokeo today; otherwise it says no verified route is known). We submit nothing for the person; the item turns clear only when a re-check passes. **Database not yet extended:** `public.hexagon_catalogue` and the ledger registry (`ledger.data_point_type`, MPC-8753) still hold exactly 366 rows and their migration and tests assert that number, so the two rows need a follow-up migration that adds them to both and updates those assertions; until then the website dataset (`public/footprint/hexagons-366.json`) and `catalogue.js` say 368 and the database says 366.

  - **Approved, built later:** "If they email us: sender details" and "mail app and timezone", from an inbound Email Worker. Plan and owner set-up: `docs/email-inbound-worker-plan-mpc-8689.md`.
