# /footprint/ data and scaling

The page lays out any number of hexagons (tested at 1, 3, 54, 118 and 1000; 1000 builds in ~150 ms).

## Item fields
`id, label, emoji, ex (example value), conf (0-100), sens (high|medium|low), cap, val, risk, group, box, state, exposure`, plus:

- `channel` — e.g. `Web`, `Email`, `Phone`. Defaults to `Web`.

## Range slider
Items of the active channel are ranked riskiest first (demo order, then asking/risk states, exposure, sensitivity). The slider is exponential, from the top 1 to the whole channel, with presets Top 3 risks / Top 10 / All.

## Channels
At the end of the slider (all of a channel shown), the other channels decode out of the matrix rain as chips with their hexagons ringed around the hive. Sliding back dissolves them. Choosing a chip makes that channel the active one; "All channels" returns to the overview.

## Trying it
`/footprint/?test=1` adds clearly-labelled synthetic channels (118 total) for testing. Nothing synthetic ships by default.

## The registry dataset (MPC-8689, MPC-11541)
`curtain.json` `"dataset": "hexagons-366.json"` loads every published data point of the Hexagon Registry. **Source:** `shared/hexagon-registry/hexagons-366.json` (file name kept, code imports it) is an export of the registry (Notion data source `40c28547-eaa7-81c6-a953-000b18c5b905`) filtered on Row Type = Data point, made with `scripts/export-registry-catalogue.mjs` (see its header for how to run it; the registry is read only). Per item: `id`, `channel` (the registry Channel Key; blank = `general`, never counted as a channel), `label` (the registry title), `evidence_key`, `status` (`defined` = registry Build Status Defined, otherwise `new`), `registry_id`, plus the existing shape. Rows already published keep their approved wording, risk tier, arrival class and slug; rows with `added` came from the 2026-11-27 export and take their fields from the registry (an empty registry field stays empty; no arrival class is filed as D). The file records the registry's Data point row count and the owner-excluded rows (538, Decision = Dropped, 2026-11-27); `scripts/build-hexagon-catalogue.mjs` and `catalogue.test.mjs` FAIL when published + excluded differs from that count. Regenerate the rest with `node scripts/build-hexagon-catalogue.mjs`.

**Status badge (MPC-11541):** every tile shows Live, In build or Planned (same words and pill as `FeatureStatus`, MPC-9836). One rule, `shared/hexagon-registry/tileState.js`: Live = one of the 54 web scan checks (nothing else is ever Live); In build = built but off (`EXTRA_HEXAGON_IDS` in `channels.js`) or already defined in the code outside the 54 (email 7, Telegram 30, X candidates); Planned = documented only. The dataset carries `tile`; the page also refuses to show a non-web item as Live. **No headline total anywhere in the copy** (owner decision 2026-11-27): the page shows per-channel counts only, and with every channel open it shows no overall total. Items with `status: "new"` are labelled "Not checked by MPT yet". Items whose `id` is already a built-in web item keep their built-in emoji, example and confidence and take only the approved risk tier (`sens`) and `tile`; the rest are added. Each item carries `slug`, and the panel links to `/hexagon/<slug>/`.

## Sample data label (MPC-9831)
Every example value on the page is demo data. Until a real scan is loaded, a banner ("Sample data — run your free scan to see your own") and a per-value marker (dotted italic value on the hexagon, a "Sample" pill in the panel) show on the first screen. A real saved scan is read from `localStorage['mpt_footprint_scan']` as `{"values":{"<hexagon id>":{"ex":"...","conf":0-100}}}`; items with a real value drop the marker, and the banner hides when any real value is present. `writeFootprintScan()` in `src/lib/webScan.ts` writes that key when a scan completes on the home page (MPC-9898; values stay in this browser, only hexagons with a real value are written). Without a scan the page stays labelled sample. Test: `e2e/footprint-sample.spec.ts`.

## The full footprint: every published data-point row, status-badged (MPC-11541)
`curtain.json` `"dataset"` now points at `footprint-datapoints.json`, generated by `node scripts/export-catalogue.mjs` from `shared/hexagon-registry/registry-datapoints.snapshot.json` (a read-only copy of the Notion registry; this repo never writes to Notion).

- **Which rows:** Row Type empty or `Data point`, **and** Decision not `Dropped`. Placeholder, Control, Framework, Feature and Dropped rows are never published. The count is derived (`footprint-datapoints.manifest.json` `count`), never typed into the data. `EXPECTED_COUNT` in the script is only the number the task expected; if the rule derives a different count the export stops and says so.
- **Badges** (`badge` on each slab): `planned` by default (copy "Not checked by MPT yet."); `live` = one of the scored items, read from the code (web `HEXAGONS` 54, enabled `TELEGRAM_HEXAGONS` 26, `EMAIL_HEXAGONS` 7, the `defined` X catalogue items 10); `in_build` = built in the code but not scored (`EXTRA_HEXAGON_IDS`, flag-off). No id is listed by hand. The export fails if a scored item is not found exactly once among the published rows.
- **No headline total** in the page copy or accessible names. Per-channel counts are shown only where a channel is shown.
- **Supabase:** `public.footprint_datapoints` (migration `20261127080000_mpc_11541_footprint_datapoints.sql`, generated, ends with a count check). `public.hexagon_catalogue` (368) is untouched because the ledger reads it row for row. CI (`supabase/tests/run.sh`) asserts `count(*)` equals `node scripts/export-catalogue.mjs --print-count`.
- **Unchanged:** the web 54, `scanCounts`, `exposure-v1`, `catalogue.js` and `hexagons-366.json` (still behind `/hexagon/`).
- Refresh: re-read the registry view, update the snapshot, run `node scripts/export-catalogue.mjs`; `--check` fails CI if the generated files are stale.
