Status: **built and tested, NOT deployed.** This moves the score users see, so it waits for Chris's explicit sign-off (the task row has `Requires_Human_Signoff`). Nothing here is switched on: no page, Worker or report reads `exposure-v2` yet.

Evidence: [`exposure-v2-mpc-11569-before-after.md`](exposure-v2-mpc-11569-before-after.md), generated by `node scripts/exposure-v2-before-after.mjs` and checked by `scripts/exposure-v2-before-after.test.mjs`.

## What changed

| | exposure-v1 (ships today) | exposure-v2 |
|---|---|---|
| Scored set | 54 web hexagons | **60** = the 54 web + the 6 built email checks |
| Formula, severities, bands, rounding | `score.js` | unchanged, imported from `score.js` |
| Weights | nine categories, sum 100 | the same nine, plus `email` 10 (**interim, approved by the owner 2026-11-27**; revisit with real data) |
| `email-breaches` | not scored | **not scored**: registry `build_status` is "not built: terms unconfirmed" (rejected with reason `not_built`) |
| Version stamp | `exposure-v1` | `exposure-v2` |

The 6: `email-name`, `email-provider`, `email-profile`, `email-libravatar`, `email-domain-record`, `email-github-commits`. The target is **60, not 61**: `email-breaches` stays In build and is not counted as Live.

A scan that runs no email check scores **exactly** the v1 score (tested over 300 random scans); only the coverage denominator grows. When email checks are in the scan the score moves because more checks are in the mix, up or down.

## Decisions (owner, 2026-11-27)

1. **Email category weight: 10, interim** (approved), with the nine v1 weights unchanged. Revisit once real scan data exists. It is `EMAIL_CATEGORY_WEIGHT` in `scoreV2.js`.
2. **Z follows whether the email checks can apply** (`totalForV2` in `scoreV2.js`): 60 when an address was given, 54 for a page-only scan, so coverage is not lowered by checks that never applied.
3. **Shadow first, flip later.** The report JSON now carries `web_scan.exposure_v2_shadow` next to `web_scan.exposure` (v1, still the headline). Nothing is shown to users from it. Flipping a user-visible score to v2 is a separate step that needs the owner's explicit go: compare shadow against v1 on real reports first, then switch (with `mpt-leads` storing `exposure-v2` as its own baseline version, never subtracted from v1).
4. **Before the flip:** a `found` probe for each of the five email checks that has only ever returned `clear` (own address, local run, recorded in `docs/probe-results/`), and the copy review of the notice and release-note wording. Telegram 30 and X 10 come after the flip, and only the checks observed returning data.

## Release notes (draft, not published)

**Your exposure score now counts more checks.**
We now check more. You did not become more exposed.
If you give us your email address, we now also look at six things that address can reveal: whether it contains a name, which mail provider it uses, whether a public profile picture exists for it (two services), whether its domain has a public ownership record, and whether it appears in public code changes. These checks are part of your exposure score and your coverage. Your score can be higher or lower than before because more checks are counted, not because anything about you changed. Scores from different methods cannot be compared, so your earlier result keeps its own version label. We still do not check your email against known data breaches: that check is not built yet.
On the scan page the same sentence appears next to your score once the new method is in use.
